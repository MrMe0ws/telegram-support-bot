# Заметки к релизу: GitHub + Telegram

## Роль

По `git log`, диффу и контексту чата готовишь **два варианта** одного релиза:

1. **GitHub** — **GitHub Flavored Markdown** (поле *Release notes* на GitHub: `##`, списки, `**жирный**`, ссылки `[текст](url)`).
2. **Telegram** — в `RELEASE_NOTES.md` хранится **plain-исходник** (без HTML/Markdown-разметки). При публикации `tools/release.py` сам собирает HTML: версия — кликабельная ссылка на GitHub Release, заголовки секций — `<b>`, в конце — кликабельный футер из `.env.release`.

Смысл обоих вариантов совпадает; **не смешивай** GFM и «телеграм-исходник» в одном блоке.

## Куда писать (обязательно)

- Файл **`RELEASE_NOTES.md`** в корне репозитория (он в git — коммитится вместе с релизом).
- При каждой генерации **полностью перезаписывай** файл; старое не дописывай.
- В чат — короткое резюме и вопрос об утверждении; полный текст — в `RELEASE_NOTES.md`.

## Структура `RELEASE_NOTES.md`

Два верхних раздела, порядок фиксированный:

```markdown
# Релиз X.Y.Z

## Вариант для GitHub Releases

…только GFM…

---

## Вариант для Telegram

…plain-исходник по правилам ниже…
```

Между блоками — строка из трёх дефисов `---` на отдельной строке.

**Теги и URL без префикса `v`:** в этом репо `2.0.0` / `…/releases/tag/2.0.0`, никогда `v2.0.0`. То же в первой строке Telegram-блока. `tools/release.py` срежет ведущий `v`, если он всё же попал в файл. (Старый тег `v1.0` — исключение из прошлого, на него не ориентируйся.)

### GitHub (GFM)

Заголовки секций **строго** (с `## `):

| Смысл | Заголовок |
|--------|-----------|
| Новые фичи | `## 🚀 Новое` |
| Улучшения без новых фич | `## ✨ Улучшения` |
| Багфиксы | `## 🐛 Исправления` |
| Внутренности / deps | `## 🧱 Технические изменения` — **обычно не нужна**, см. «Стиль» |
| Что сделать при обновлении | `## ⚠️ При обновлении` — только если есть обязательные шаги |

Порядок: **🚀 Новое** → **✨ Улучшения** → **🐛 Исправления** → (редко) **🧱 Технические изменения**. Опционально: `## ⚠️ Breaking changes` / `## ⚠️ При обновлении` в конце. Если релиз ломает совместимость (как 2.0.0 с Remnawave 3.x) — допустим отдельный первый раздел `## 🚨 Главное`.

Списки `- `, жирный `**…**`, ссылки GFM. Весь блок GitHub **не** оборачивай в fenced code. Переменные окружения и команды — в `` `коде` ``.

**Никаких цитат (`>`), `<blockquote>` и `<details>`** — сворачивание секций существует только в телеграм-посте (см. «Свёрнутые цитаты»). В GitHub все пункты видны сразу.

### Telegram (plain-исходник в файле)

В файле **никакой** разметки HTML/Markdown: не используй `##`, `**`, `` ` ``, `<b>`, `<a>`, `[текст](url)`.

**Первая строка** — версия и URL релиза на GitHub через пробел:

```text
2.1.0 https://github.com/MrMe0ws/telegram-support-bot/releases/tag/2.1.0
```

Допустимо также: `2.1.0 (https://github.com/...)`. Репозиторий: `MrMe0ws/telegram-support-bot`.

**Заголовки секций** — строка без `##`:

- `🚀 Новое`
- `✨ Улучшения`
- `🐛 Исправления`
- `🧱 Технические изменения` — обычно не писать
- опционально: `⚠️ Breaking changes` / `⚠️ При обновлении` / `🚨 Главное`

Любая строка, которая не начинается с `•`, считается заголовком новой секции — поэтому каждый пункт пиши **одной строкой** с `•` в начале.

**Пустые строки:**
- между **пунктами** одной секции — **одна пустая строка**;
- между **секциями** — **две** пустые строки;
- между заголовком секции и первым `•` — **одна** пустая строка;
- первая строка (версия + URL) отделена от первой секции **одной** пустой строкой.

`tools/release.py` при сборке HTML **сам** выставляет эти отступы, даже если в файле их забыли.

**Не** добавляй в файл футер — его дописывает `tools/release.py` из `.env.release`.

Порядок секций тот же, что в GitHub. Пустые секции не выводи.

**GitHub (GFM):** между `- ` пунктами пустые строки **не** ставь — иначе Markdown разобьёт список.

### Лимит Telegram: 4096 символов (жёсткий)

Telegram Bot API не принимает сообщение длиннее **4096 символов**. Считается текст, а не разметка. `tools/release.py` проверяет длину перед отправкой и падает с понятной ошибкой; `preview` печатает текущую длину.

Практика: **держи телеграм-блок в пределах ~3800 символов**, оставляя запас на футер. GitHub-вариант в лимит не упирается — сокращать нужно только телеграм-блок: варианты совпадают по смыслу, не по длине.

Как сокращать:
- убрать вводные обороты и повторы, оставить «что изменилось + что это даёт»;
- склеить однотипные мелкие пункты в один;
- вынести детали в GitHub-вариант, в Telegram оставить одну фразу.

### Свёрнутые цитаты — ТОЛЬКО в Telegram (делает CLI сам)

`tools/release.py` оборачивает пункты секции в `<blockquote expandable>`, когда в секции **три пункта и больше** и это одна из второстепенных секций: `✨ Улучшения`, `🐛 Исправления`, `⚠️ При обновлении`, `🧱 Технические изменения`, `⚠️ Breaking changes`. `🚀 Новое` не сворачивается никогда.

В `RELEASE_NOTES.md` ничего для этого делать не нужно. В свёрнутой секции первый пункт виден в превью — **самый важный пункт ставь первым**.

В GitHub Release уходит сырой GFM-блок из файла, мимо форматтера, — разделение закреплено тестом `test_github_body_has_no_telegram_markup` (`tests/test_release_tool.py`).

## Источник правды

1. `git log` / при необходимости `git show`, узкий `git diff`.
2. Контекст чата.
3. Конфликт — приоритет репозиторию.

## Стиль (аудитория — владелец бота поддержки)

Changelog читают те, кто держит этот бот у себя: админы VPN-сервисов, часто без опыта разработки. Цель — **суть обновления и польза**, без воды.

**Пиши:**
- что изменилось для клиента / сотрудника поддержки / админа и **что это даёт**;
- коротко, по-человечески, без жаргона;
- новые настройки — названием переменной из `.env` и одной фразой, что она делает и что по умолчанию.

**Не пиши:**
- имена файлов, модулей, функций, классов, commit hash;
- внутренние детали без видимого эффекта (рефакторинг, тесты, устройство очередей);
- секцию **🧱 Технические изменения** — по умолчанию пропускай.

### Как обновляется бот (важно — не путать админов)

Готового образа в реестре **нет**: админ собирает контейнер из исходников на своём сервере (`docker compose build`). Поэтому шаг обновления — это:

```text
git pull, затем docker compose up -d --build
```

Схема базы (SQLite) обновляется **сама при старте** бота — новые колонки и таблицы добавляет `init_db`.

- **Не пиши:** «примените миграции», «выполните SQL», «пересоздайте базу».
- **Пиши** (если схема менялась): одной фразой к обновлению, например: «Обновите код и пересоберите контейнер — база обновится сама при старте.»

Что ещё бывает в «⚠️ При обновлении» (только если реально нужно):
- новые обязательные переменные в `.env` — назвать коротко (необязательные с разумным значением по умолчанию — в описании фичи, не здесь);
- новый том в `docker-compose.yml` (например, `./knowledge:/app/knowledge:ro` для базы знаний ИИ) — тем, кто правил compose под себя;
- новые права бота в группе (например, «Управление темами»);
- изменения в поведении по умолчанию, которые админ заметит сразу (новый значок темы и т. п.) и как их выключить.

### Как найти точку отсчёта (всегда, до чтения `git log`)

```bash
git fetch --tags origin
git tag --list '[0-9]*' --sort=-v:refname | head -5   # только релизные теги, без v1.0/remove
git log --oneline <последний_тег>..HEAD
```

Ловушки:

1. **Без `git fetch --tags` последнего релиза в клоне может не быть** — `gh` создаёт тег на стороне GitHub.
2. **`git tag --sort=-v:refname | head -1` врёт:** в репо есть посторонние теги (`v1.0`, `remove`). Отсюда фильтр `--list '[0-9]*'`.
3. Проверка: `git log -1 --format='%h %ci %s' <тег>` — коммит тега должен быть вершиной `main` на момент прошлого релиза.

Номер нового релиза: есть новые фичи — минорный шаг (`2.0.0` → `2.1.0`), только исправления — патч, ломается совместимость — мажор.

### Точка отсчёта — предыдущий РЕЛИЗ, а не начало разработки

**«Улучшения» и «Исправления» описывают разницу с предыдущей released-версией.** Если баг возник и был починен внутри текущего цикла, у читателя его никогда не было — пункт не нужен.

| Ситуация | Куда |
|----------|------|
| Фича новая целиком | `🚀 Новое` — одним пунктом (или несколькими по смыслу), включая её доводки |
| Баг был в предыдущем релизе, починен сейчас | `🐛 Исправления` |
| Баг появился и умер внутри текущего цикла | **никуда** |
| Доводка новой фичи | **никуда** — фича описывается сразу в готовом виде |
| Улучшение того, что было в предыдущем релизе | `✨ Улучшения` |
| Баг был в коде, но в прошлом релизе ни на что не влиял | **никуда** |

Сомневаешься — `git show <прошлый_тег>:<файл>` и проверь, что было в релизе.

## Workflow публикации (обязательно)

1. Сгенерируй / перезапиши `RELEASE_NOTES.md`, прогони `python tools/release.py preview` (разбор и длина поста).
2. Кратко покажи в чате версию и суть; спроси: **устраивает ли текст? Публиковать?**
3. **Стоп.** Пока нет явного положительного ответа (`да` / `ок` / `публикуй` / аналоги) — **не** создавай release и **не** шли в Telegram.
4. После согласия:
   1. **Коммиты должны быть на `main` в origin.** `gh release create` без `--target` берёт тег с HEAD default branch. Закоммить `RELEASE_NOTES.md` и запушь `main` до публикации.
   2. Превью: `python tools/release.py preview`
   3. Публикация: `python tools/release.py publish` (или по отдельности `github` / `telegram`). Если Telegram упал (лимит, сеть) — поправь и повтори только `telegram`: GitHub Release уже создан, повторный `github` упадёт.
   4. Верни в чат URL GitHub Release и факт отправки в тему.

Конфиг: локальный **`.env.release`** (образец — `.env.release.sample`, файл в `.gitignore`). Токен announce-бота — только там, **никогда** в git и не в чат.

`RELEASE_TG_PROXY_URL` — только `http://` прокси (стандартная библиотека не умеет SOCKS; у Clash/FlClash HTTP на порту mixed, обычно `http://127.0.0.1:7890`). Если прокси не поднят, CLI повторит отправку напрямую — только когда запрос заведомо не ушёл, чтобы не задвоить анонс.

CLI — `tools/release.py`, только стандартная библиотека Python, **не** входит в Docker-образ (Dockerfile копирует лишь `app/` и `texts/`). Нужен установленный и залогиненный `gh`.

## Активация

Релизноты, changelog, текст для канала + GitHub, перезапись `RELEASE_NOTES.md`, публикация релиза.
